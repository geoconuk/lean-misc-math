# Contributing

## How work is divided here

The selection of results — what is worth formalising, how it should be stated, and
whether a generated result is worth keeping — is George Constantinides's contribution.
The Lean statements and proofs are generated by Claude, kernel-verified and
axiom-audited, and not read by a human. See
[Who did what](README.md#who-did-what).

Contributions are welcome on both sides of that line, but they are different kinds of
work and it is worth saying which you are offering.

## The most useful thing you can do

Tell us a **statement** is wrong.

Everything in this repository is proved by Lean's kernel and audited for axiom use, so
"the proof is broken" is not a failure mode that can occur. What can and does occur is a
statement that is correctly proved and non-vacuous but does not say what its docstring
claims — because it quantifies over the wrong object, leans on truncated `Nat`
subtraction or a junk-value convention, or is expressed in terms of a bespoke definition
rather than Mathlib's. No automated check catches that, and the proofs here are not
reviewed by a human.

Open an issue with the module name, the statement, and what you think it should say.
Those reports are the point of the [`## Informal statement`](README.md#reviewing-a-result-in-thirty-seconds)
convention, and they are worth more than new results.

## Adding a result

1. Copy [`docs/TEMPLATE.lean`](docs/TEMPLATE.lean) to `MiscMath/<Area>/<Result>.lean`.
2. Fill in the informal statement, source, and provenance. If a result already exists in
   Mathlib, say so under `## Relation to Mathlib` rather than quietly duplicating it.
3. State the theorem **in Mathlib's vocabulary**. If you must introduce a definition, ship
   a characterisation lemma tying it back to Mathlib's, and say why the new definition was
   necessary.
4. Write the sanity checks. If the theorem has hypotheses, a satisfiability witness is
   mandatory — see below.
5. Add the `import` line to `MiscMath.lean`, alphabetically.
6. Run the checks:

```bash
lake build && ./scripts/check-imports.sh && ./scripts/check-conventions.sh
```

## Why witnesses are mandatory

A theorem with unsatisfiable hypotheses is vacuously true and provable with no
mathematical content whatsoever. It passes the kernel, it passes the axiom audit, and it
is worthless. This is the single most likely way for a machine-generated result to be
simultaneously correct and useless, so every result with hypotheses carries an `example`
exhibiting values that satisfy all of them at once.

Include universally quantified hypotheses in the witness. `∀ p, P p → Q p` is easy to
satisfy accidentally and easy to make unsatisfiable in combination with the others; it is
where a vacuous statement most often hides.

## Style

Mathlib's [naming](https://leanprover-community.github.io/contribute/naming.html) and
[style](https://leanprover-community.github.io/contribute/style.html) conventions, aimed
at but not enforced. Prefer the shape an application will actually want — a primality
criterion is more useful than the existential it is contraposed from, so ship both.

## Citing

If you use these results, please cite the repository — see
[Citing](README.md#citing) and [`CITATION.cff`](CITATION.cff). The selection and
curation of results is the contribution being credited.

## Upstreaming

If a result here would benefit a wide audience, the right destination is Mathlib, not this
repository. The licence (Apache 2.0) matches Mathlib's so that this is purely a question
of review effort. Note that Mathlib has its own policy on AI-assisted contributions and
expects a contributor who can stand behind the work under review; "it compiled" is not
sufficient there, by design.
